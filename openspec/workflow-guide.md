# OpenSpec 工作流程指南

## 概述

OpenSpec 是一个规范驱动的开发工作流程，旨在通过结构化的变更提案来管理项目开发。本文档介绍如何在 Genshin-Calc 项目中使用 OpenSpec 工作流程进行协作开发。

## 核心概念

### 1. 项目上下文 (Project Context)
- **文件**: `openspec/project.md`
- **作用**: 定义项目的基本信息、技术栈、编码约定和领域知识
- **重要性**: 为 AI 助手和开发人员提供项目背景，确保所有变更都符合项目规范

### 2. 变更提案 (Change Proposal)
- **文件**: `openspec/proposals/[proposal-name].md`
- **作用**: 详细描述计划的功能变更、技术实现和影响分析
- **重要性**: 确保所有变更都经过充分思考和审查

### 3. 规范应用 (Spec Application)
- **命令**: `.roo/commands/openspec-apply.md`
- **作用**: 将批准的变更提案应用到实际代码中
- **重要性**: 确保实现与规范一致

## 工作流程详解

### 阶段 1: 规划与提案

#### 1.1 识别需求
- 用户提出新功能需求或问题
- 开发人员分析需求的可行性和影响
- 确定是否需要创建变更提案

#### 1.2 创建变更提案
```bash
# 在 openspec/proposals/ 目录下创建新的提案文件
# 文件命名格式: [feature-name].md
```

**提案必须包含以下部分**:
- 基本信息 (ID、状态、优先级等)
- 变更概述
- 问题陈述
- 解决方案
- 技术实现
- 用户界面设计
- 实施计划
- 测试策略
- 风险评估
- 成功指标

#### 1.3 提案审查
- 技术负责人审查技术可行性
- 产品负责人审查用户价值
- 团队成员审查实施计划
- 根据反馈修改提案

### 阶段 2: 批准与规划

#### 2.1 状态管理
提案状态流转:
```
草案 → 审阅中 → 已批准 → 实施中 → 已完成 → 已发布
```

#### 2.2 优先级排序
- 根据业务价值和技术复杂度确定优先级
- 高优先级提案优先分配资源
- 考虑依赖关系和发布时间窗口

#### 2.3 资源分配
- 为已批准的提案分配开发人员
- 估算工作量和时间线
- 纳入开发迭代计划

### 阶段 3: 实施与开发

#### 3.1 规范应用
使用 `.roo/commands/openspec-apply.md` 命令:
```markdown
请应用 openspec/proposals/[proposal-name].md 中的变更提案
```

#### 3.2 开发流程
1. **创建功能分支**: `git checkout -b feature/[proposal-id]`
2. **实现代码**: 根据提案中的技术实现部分编写代码
3. **编写测试**: 按照提案中的测试策略实现测试
4. **更新文档**: 更新相关文档和注释

#### 3.3 质量保证
- 代码审查确保符合项目约定
- 自动化测试验证功能正确性
- 性能测试确保满足性能要求

### 阶段 4: 验证与发布

#### 4.1 功能验证
- 对照提案中的成功指标进行验证
- 进行用户验收测试
- 确认所有验收标准都已满足

#### 4.2 提案更新
- 更新提案状态为"已完成"
- 记录实际实施时间和结果
- 添加经验教训和改进建议

#### 4.3 发布准备
- 准备发布说明
- 更新版本号
- 部署到测试环境进行最终验证

## 协作指南

### 开发人员角色

#### 1. 功能开发者
- **职责**: 根据批准的提案实现功能
- **工作流程**:
  1. 阅读并理解提案内容
  2. 创建功能分支
  3. 实现代码和测试
  4. 提交代码审查
  5. 根据反馈修改代码
  6. 合并到主分支

#### 2. 技术审查者
- **职责**: 审查提案和代码的技术可行性
- **审查要点**:
  - 架构设计是否合理
  - 代码质量是否符合标准
  - 性能影响是否可接受
  - 安全性是否得到保障

#### 3. 产品负责人
- **职责**: 确保变更符合产品方向和用户需求
- **审查要点**:
  - 用户价值是否明确
  - 用户体验是否良好
  - 功能优先级是否合理

### AI 助手协作

#### 1. 架构模式 (🏗️ Architect)
- **使用场景**: 创建和审查变更提案
- **交互方式**:
  ```
  "请为 [功能描述] 创建一个 OpenSpec 变更提案"
  "请审查 openspec/proposals/[proposal-name].md 提案"
  ```

#### 2. 代码模式 (💻 Code)
- **使用场景**: 实施批准的变更提案
- **交互方式**:
  ```
  "请应用 openspec/proposals/[proposal-name].md 中的变更"
  "请根据提案中的技术实现部分编写代码"
  ```

#### 3. 调试模式 (🪲 Debug)
- **使用场景**: 解决实施过程中的问题
- **交互方式**:
  ```
  "实施提案时遇到了 [问题描述]，请帮助调试"
  ```

### 最佳实践

#### 1. 提案编写
- **具体明确**: 避免模糊的描述，提供具体的实现细节
- **考虑全面**: 包括技术、用户、性能等各个方面
- **可衡量**: 定义明确的成功指标和验收标准
- **现实可行**: 评估技术复杂度和资源需求

#### 2. 审查流程
- **及时反馈**: 尽快提供审查意见，避免阻塞开发流程
- **建设性意见**: 提供具体的改进建议，而非简单的批评
- **多角度审查**: 从技术、产品、用户等不同角度审查

#### 3. 实施管理
- **遵循提案**: 严格按照批准的提案进行实施
- **及时沟通**: 遇到问题及时沟通，不要擅自修改方案
- **质量优先**: 确保代码质量，不为了速度牺牲质量

## 常见问题

### Q1: 是否所有变更都需要提案？
A1: 不是。简单的 Bug 修复或小型改进可以简化流程，但涉及架构变更、新功能或重大改进的变更需要完整提案。

### Q2: 提案被拒绝怎么办？
A2: 根据审查意见修改提案，重新提交。如果根本不可行，可以考虑替代方案或放弃该变更。

### Q3: 如何处理紧急变更？
A3: 紧急变更可以先实施，后补提案。但必须在事后尽快完成文档化和审查。

### Q4: AI 助手如何理解项目上下文？
A4: AI 助手会首先读取 `openspec/project.md` 文件，了解项目的技术栈、约定和领域知识，然后基于这些信息处理请求。

## 总结

OpenSpec 工作流程通过结构化的变更提案和明确的角色分工，确保项目开发的有序性和质量。关键是要：

1. **充分规划**: 在实施前仔细思考和分析
2. **规范文档**: 使用标准格式记录所有变更
3. **严格审查**: 从多个角度审查提案和实现
4. **持续改进**: 根据经验不断优化工作流程

通过遵循这个工作流程，团队可以更高效地协作，减少沟通成本，提高代码质量，确保项目朝着正确的方向发展。
